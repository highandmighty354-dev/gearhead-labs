# V1.1.0 Gearhead Labs Mathematical QA Protocol

## Purpose
Validate Gearhead Labs as an engineering-grade automotive mathematics platform. Every calculator must be independently checked for mathematical correctness, dimensional consistency, unit integrity, numerical behavior, edge cases, and automotive plausibility.

## Non-Negotiable Standard
A calculator is not considered correct because it returns a number or because its formula looks reasonable. Expected results must be independently derived or independently verified.

## Audit Layers

### 1. Inventory Audit
- Confirm every calculator has a unique ID.
- Confirm every calculator is reachable through the production navigation.
- Confirm the production target remains 575 calculators + Dashboard.
- Confirm Lab/category assignments and counts.

### 2. Formula Audit
For each calculator:
- Identify the governing equation.
- Rewrite the equation independently.
- Verify every constant and conversion factor.
- Check dimensional consistency.
- Check assumptions and applicable operating ranges.
- Identify hidden approximations and rounding.

### 3. Numerical Test Suite
Each calculator receives deterministic test vectors including:
- Nominal/reference case.
- Low-boundary case.
- High-boundary case.
- Zero case where mathematically meaningful.
- Near-zero case where meaningful.
- Invalid-input cases.
- Unit-conversion cases.
- Precision/rounding cases.

### 4. Independent Expected Values
Expected outputs must come from an independent implementation or hand-derived reference equation, not from the calculator under test.

### 5. Unit Verification
- Imperial and Metric inputs must agree after conversion.
- Output units must match the displayed label.
- Conversion factors must be verified.
- Round-trip conversions must remain within defined tolerance.

### 6. Engineering Sanity Checks
Results must be physically plausible for automotive applications. Plausible-looking numerical output is not sufficient evidence of correctness.

### 7. Cross-Calculator Consistency
Where two or more calculators represent inverse or related relationships, their outputs must reconcile within defined tolerances.

### 8. Failure Classification
Every defect is classified as one or more of:
- Formula error
- Constant error
- Unit/conversion error
- Input validation error
- Boundary/edge-case error
- Numerical precision error
- Display/result error
- Navigation/integration error
- Documentation/assumption error

### 9. Repair Protocol
1. Reproduce the defect.
2. Determine root cause.
3. Correct the underlying implementation.
4. Add a regression test vector.
5. Re-run the affected calculator.
6. Re-run related calculators where dependencies exist.
7. Verify the live production build.

### 10. Release Gate
No calculator-library milestone is complete until:
- All discovered defects are resolved or explicitly documented.
- All tested calculators pass their required vectors.
- No critical mathematical or unit defects remain.
- Navigation reaches the intended calculators.
- Production behavior matches the audited implementation.

## QA Philosophy
Think like a mathematician, mechanical engineer, software test engineer, and experienced automotive technician simultaneously. The objective is not merely to find bugs; it is to establish evidence that the mathematics can be trusted.
