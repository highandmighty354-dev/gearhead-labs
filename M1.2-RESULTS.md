## Method

1. **Inventory first** (`M1.2-INVENTORY.md`). The live renderer as it actually runs (`RENDERS[id]`; for `dynamic_compression`, the object method captured by the `oldDCR` wrapper) and the registry entry, per calculator, before any change.
2. **Harness defects fixed before judging the registry.** All three make the check stricter, never looser:
   - **H1:** a live "Validation required" / "Invalid …" box is treated as a live INVALID state, and the engine must return `null`. Before, it was reported as "no matching result".
   - **H2:** every live input with no registry variable is also probed at 0, not only scaled. This catches inputs that control validity only.
   - **H3:** every option of a numeric select bound to a registry input is tested.
   - All 215 previously migrated calculators still pass under the stricter harness.
3. **Minimal registry corrections** (`edit_registry.py`, `m12-registry-edits.json`). The registry now enforces the same guard as the live renderer: in each corrected entry, the formula (math unchanged) is wrapped as `guard ? (formula) : NaN`.
   - Entries appear once in the file text; at runtime `Object.assign(GH_LEGACY_FORMULAS, GH_BACKFILL_FORMULAS)` shares the same object, so duplicates cannot diverge.
   - **No change to `gh-engine.js`. No formulas in the engine. No live renderer changed.**
4. **Proof.** LIVE_PARITY on the finished build: defaults, all ×1.07, each input ×1.13, each input = 0, every numeric-select option, every unbound live input probed. It compares value at displayed precision (or ≤0.1%), unit, and validity.
5. **Visitor-facing check.** Rendered calculator text is compared before/after (0 of 25 changed). The published formula block is compared before/after, which led to a new gate suite, **FORMULA_DISPLAY**, after a display regression was found and reverted (see `bearing_life`).
6. **Negative controls.** Each fails as it should:
   - `tire_size` guard reverted to `: 0` → LIVE_PARITY fails
   - `brake_bias` without its validity input → LIVE_PARITY fails twice (validity + H2)
   - the `||NaN` display form re-introduced → FORMULA_DISPLAY fails

## Notable cases

- **The most common defect (13 of 22 corrections): the registry copied the live guard but returned `0` on invalid input.** The live page shows "Invalid …" instead. This is Unknown → Zero inside the source of truth. Now `NaN` → engine `OUT_OF_RANGE`.
- **`e85_blend`: a real branch mismatch, not just a guard.** The registry computed "Fuel to Remove" whenever target < current. Live computes it only when target < current **and** E85 cannot reach the target, and shows "—" for any amount ≤ 0. The registry now mirrors the live branches exactly. Spot-checked in the live page: target 5% from 10% → Remove 1.14 gal, Add "—", on both sides.
- **`brake_bias`:** the live page shows weight transfer only when Static Front Weight % is in (0,100). That input doesn't enter the transfer math, but it controls validity. It was added to the registry, used in the guard only. This was found by the new H2 probe, and is the one DOMAIN case whose input list changed.
- **`master_cylinder`:** output 4 was a byte-identical duplicate of output 1 ("Pushrod Force"), which gave the engine a duplicate key. Removed. The published formula no longer lists Pushrod Force twice.
- **`hp_from_specs`:** the live page converts CFM to mass with an Air Density input (default 0.0765). The registry hard-coded 0.0765; it now uses the input. The published formula now shows the variable instead of a hidden constant.
- **`reverse_displacement`:** the live page displays a 0 result as "—". The first encoding (`(v)||NaN`) was correct but **leaked code into the published formula**. It was replaced with `(known>0 && (v)!==0) ? (v) : NaN`, which typesets identically to before.
- **`bearing_life` (left pending, deliberately).**
  - The live Bearing Type select (3 → p = 3 ball; 3.33 → p = 10/3 roller) was encoded, and it **passed LIVE_PARITY**.
  - But every faithful registry form typesets in the visitor-facing formula block as code, e.g. `(rated_load/load_br)^life_exp===3?3:10/3`. The form `^10/3` reads as ((C/P)^10)/3, which is mathematically misleading.
